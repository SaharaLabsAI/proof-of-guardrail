Proof-of-Guardrail in AI Agents,
and What (Not) to Trust from It

Xisen Jin1,2, Michael Duan2, Qin Lin1, Aaron Chan1, Zhenglun Chen1, Junyi Du1, Xiang Ren1,2
1Sahara AI, 2University of Southern California
Github (OpenClaw Demo) Arxiv

We propose proof-of-guardrail—a lightweight system that allows agent developers to produce cryptographic proof that a response is generated after an open-source guardrail, without revealing their private agent implementation.

Proof-of-guardrail is enabled by Trusted Execution Environments (TEEs) and remote attestation— a technology that executes code in a hardware-enforced isolated environment and produces a cryptographically signed statement describing the exact code that ran.

Proof-of-Guardrail via TEE Attestation

We build proof-of-guardrail using remote attestation inside a Trusted Execution Environment (TEE). A TEE is a hardware-enforced isolated runtime. When a program is loaded into a TEE, the hardware measures its exact binary and produces a signed attestation document that includes this measurement. This document cannot be forged by the OS, hypervisor, or developer—only the hardware TEE key can sign it.

🔑 Core Idea. The TEE measures the loaded wrapper program (including the guardrail) and signs an attestation document that includes a commitment Hash(input, response) of the input and the response. Any user can verify the attestation document to confirm that the exact open-source guardrail produced the response from the input.

System Pipeline
1
Load & Measure. The wrapper program—bundling the guardrail and its configuration—is loaded into the TEE. The hardware records enclave measurement m = Hash(program).
2
Secret Injection. The developer's private agent is passed as secret input. The agent is not visible to users.
3
Guarded Execution. For each input, the wrapper program runs the agent and enforces the guardrail on all inputs, tool calls, and outputs to produce a response.
4
Attestation Generation. The TEE produces a signed attestation document that binds the measurement m and Hash(input, response). A fresh attestation is generated per input.
5
User Verification. The user receives the response and attestation document, then verifies offline: (i) signature valid under TEE platform key, (ii) measurement m matches expected open-source wrapper program, (iii) commitment matches Hash(input, response).
How the Desiderata Are Met

① Computational Integrity

The measurement m covers the exact binary of the wrapper program, including guardrail code. Any modification to the guardrail changes m and fails verification, proving that the response was generated after the declared guardrail.

② Confidentiality of Agent

The agent is the secret input to the enclave and never appears in the attestation document. The developer's proprietary implementation remains private.

③ Public Input/Output

By the nature of the cryptographic signature, the attestation document cannot be tampered with or fabricated even if input, response, and attestation document are all public — as is typical when the agent chat with users over the agent developer's account on a chatting app.


Experiments

We evaluate end-to-end feasibility on OpenClaw agents (backed by GPT-5.1) on an AWS m5.xlarge instance with AWS Nitro Enclaves TEE, using two open-source guardrails: Llama Guard 3-8B (for content safety, on ToxicChat dataset) via API and Loki fact checking tool (on FacTool-KBQA dataset).

What Not to Trust from Proof-of-Guardrail

⚠ Critical caveat: Proof-of-guardrail proves that a specific guardrail executed. It does not prove that the response is safe.

Although proof-of-guardrail reduces the attack surface of malicious developers by ensuring guardrail execution, it should not be interpreted or advertised as proof-of-safety.

Guardrails can make errors and be jailbroken

Although proof-of-guardrail ensures execution of the guardrail, the guardrail itself can still make errors—as shown in the imperfect F1 scores in our experiments. Furthermore, because proof-of-guardrail requires the guardrail to be open-source, a malicious agent developer can perform jailbreak attacks against it, crafting inputs that reliably evade detection while still producing valid attestation proofs.

Potential vulnerabilities in the wrapper program

The measured wrapper program itself should not have vulnerabilities that allow the agent to bypass the guardrail, e.g., by executing arbitrary commands inside the enclave. A good solution is restricting the late-injected agent to non-executable prompt artifacts, thereby minimizing unexpected risks introduced by the agent while addressing all vulnerabilities in the measured wrapper program.
